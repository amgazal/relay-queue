# Engineering decisions

| Decision | Benefit and cost |
| --- | --- |
| Use PostgreSQL as the queue | Job state, attempt history and scheduling can commit atomically using one storage system. PostgreSQL must absorb queue writes, index maintenance, scans and application reads. Relay offers job execution semantics; replayable event streams and fan-out subscriptions are outside its scope. |
| Claim with row locks and SKIP LOCKED | Independent workers can claim eligible rows in priority order without waiting for a peer's locked row. Ordering applies among available rows, and lower-priority jobs can wait under sustained high-priority load. The transaction ends before handler execution. |
| Couple a lease deadline with a per-claim token | The deadline makes abandoned work recoverable. The token identifies a particular attempt even when the same worker reclaims the job. Finalization locks the row and checks PostgreSQL time. Shorter leases recover sooner and leave less room for database stalls. |
| Allow repeated execution | The worker can lose its lease after an external service commits and before Relay records success. A database transaction cannot cover that remote effect. The handler must carry a stable identity for the receiver to deduplicate. |
| Distinguish submission keys from event IDs | The global submission key compares immutable original parameters, including delay and original attempt budget. Identical replays return the job's current state; conflicts return 409. Two independently submitted jobs can carry the same business event. The demo receiver enforces event uniqueness with its own primary key. |
| Keep a retry budget and attempt ledger | Retryable errors and expired claims use capped exponential backoff with jitter. A permanent failure goes directly to dead. Manual retry makes the job eligible again and increments its budget. Operators retain the original attempts and their errors; the history and its indexes grow over time. |
| Persist UTC cron occurrences | Dispatchers skip locked schedules, insert an ordinary job and advance next_run atomically. The unique schedule ID and occurrence time protect against duplicate job records. After an outage, Relay dispatches the oldest pending occurrence once and skips intermediate matches. This bounds recovery load and sacrifices per-tick catch-up. |
| Serialize optional admission limits | When enabled, API and scheduler admissions coordinate with a transaction advisory lock and an exact active-job count. Both queued and running jobs occupy capacity; retries keep their slots. Strict limits require consistent replica configuration and cooperating producers. Serialized writes and counts cost throughput. |
| Bound concurrency per process | Each slot claims one job. Adding workers shortens queue wait while increasing demand on the shared database. In the measured scaling bursts, four to eight processes improved median completion throughput about 4.5%, with overlapping run ranges. This evidence does not isolate a limiting query. |
